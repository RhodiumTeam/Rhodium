# 以状态表为准，事件表只用于通知和续传

这篇回答：Rhodium 的数据库里哪份数据算数，事件记录拿来做什么。

前置阅读：[术语表](../../GLOSSARY.md)、[调研摘要](../research.md)

状态：已接受（2026-10-21）

Rhodium 用一个 SQLite 文件记两类东西。状态表记“现在是什么样”，例如槽位的模式、哪条提问没答、Bot 绑到哪。事件表记“发生过什么”。

以状态表为准。每次变化直接改状态表，并在同一个事务里追加一条事件。另一种做法叫事件溯源：只以事件为准，现状从事件算出来。Rhodium 不这样做。

每条事件带一个全局递增的序号。事件表只用来做三件事：

- 让看板实时刷新。
- 让断线的客户端从某个序号接着收，例如 v2 的 Bot 程序。
- 排障时查一条消息经过了哪些步骤。

不用事件溯源，不影响可靠投递。例如结局不明的消息不自动重发，这类规则照样采用，见[调研摘要](../research.md) §2。

## 考虑过的其他方案

- **事件溯源**，也就是以事件日志为准，状态表从日志算出来。每加一个功能，都要先设计事件，再写把事件算成状态的代码。事件一旦存进库就不能改含义，要另写升级程序。估算多约 1000 行。v1 正是需求每周在变的时候，这个代价最高。T3 Code 走的就是这条路，它的编排器一个文件约 1.2 万行。

## 后果

- 状态表写坏了，没法从事件重算，只能从每日备份（保留 14 份）恢复。单用户单机，这够用。
