# Bot 程序 API 用 Satori 子集，不用 OneBot

这篇回答：v2 的 Bot 程序通过什么协议和 Rhodium 对接。

前置阅读：[术语表](../../GLOSSARY.md)、[产品说明](../product.md)、[调研摘要](../research.md)

状态：已接受（2026-10-21）。2026-10-23 补了这一期怎么落地，2026-10-24 又改了几条，见文末。

Satori 是 Koishi 社区的跨平台聊天机器人协议：一个 WebSocket 事件流，加一组 HTTP 方法。Rhodium 在本机当 Satori 服务端，只实现现成客户端用得到的一小块。Satori 没有的能力，例如流式、命令菜单、扫码建 Bot，用规范允许的扩展方式补上。

选 Satori，是因为现成的 Bot 能直接接入。Koishi、NoneBot、Entari、AstrBot 的 Satori 客户端都能原样连上。Entari 项目的示例配置默认就连 `ws://127.0.0.1:5140/satori`。验收场景见[产品说明](../product.md) §8。

## 考虑过的其他方案

- **OneBot**。它是另一个常见的聊天机器人协议，围绕个人 QQ 号设计。它的 QQ 实现基本都是模拟个人号的非官方客户端，例如 NapCat，有封号风险。Rhodium 只用官方 Bot 接口，和这个生态对不上。Rhodium 也明确不要它。
- **自定一套私有 API**。没有任何现成的客户端和框架能接。

## 后果

- 扩展部分只有 Rhodium 认。用标准客户端写的 Bot 程序，只能用到标准那一块。
- 上游的 Satori 服务端在断线续传上都有毛病（[调研摘要](../research.md) §5）。Rhodium 只照协议的形态做，不照搬实现。
- 接口只开在 `127.0.0.1`。
- 每个 Bot 程序连接时要带一个 token。Bot 程序和 Rhodium 是同一个系统用户，所以 token 只防误用，不防恶意。

## 2026-10-23 补充：这一期怎么落地

上面的决定不变。2026-10-23、2026-10-24 为 Bot 程序这一期拷问了两轮，补下面几条。行为规则见[产品说明](../product.md) §8，调研依据见[调研摘要](../research.md) §5。

- **每个程序一个独立进程，Rhodium 只管进程，不管里面。** 程序就是一条命令、一个目录、一个令牌。Entari 项目只是其中一种：Entari 本身是 Satori 客户端，连上来的就是真的 Entari 进程，插件代码不经过 Rhodium。
  - 没选“Rhodium 托管一个共享的 Entari，agent 往里放插件”：一个插件卡住，所有 Bot 一起停；依赖挤在一个环境里；进程里守不住“每个程序只看得到自己的 Bot”；Rhodium 还得跟着 Entari 改版走。
  - 没选“插件跑在 `rhodium` 进程里”：插件崩了，IM 和所有 agent 一起停，和 [ADR-0002](0002-one-daemon-plus-holders.md) 分进程的思路相反，也不兼容 Entari。
- **进程用 systemd 的临时服务管，不用托管进程。** 托管进程的价值是攥住 agent 的标准输入输出，Bot 程序走网络，用不上。systemd 自己会重启、收日志，`rhodium` 重启也碰不到它。
  - 熔断的次数由 Rhodium 自己数。2026-10-23 实测：systemd 数的是启动次数，跑久了的程序要多退出一次才熔断。
- **只保证 Entari。** 只测 satori-python 这一个客户端。外加三条几乎不花钱的兼容：事件的旧字段 `id` 等于 `sn`；新旧两套请求头都认；不发缺用户信息的登录。Koishi、NoneBot 等到真要接时再测。
- **实现范围是最小集，加上按钮、引用和发文件。** 规则是：Entari 支持的才做。Entari 支持标准按钮和按钮事件、引用、发文件，不支持 Markdown 元素和命令菜单注册。所以这一期不开任何扩展。上面说用扩展补上的流式、命令菜单，都不做；扫码建 Bot 走 `rh`，不走 Satori。
  - 2026-10-24 加的：链接按钮两个平台都用真的；收到的引用交给程序，所以多做 `message.get`；程序能发引用、发文件。
- **事件序号持久、按程序计数，事件本身只在内存里。** 上游服务端的序号只在内存里、重启归零，续传形同虚设。Rhodium 把每个程序的序号存进库，重启后接着往上数；最近一小时的事件留在内存里，程序断线重连时带上序号就能补发。
  - Rhodium 停着时别人发的消息，平台在它起来后补发，照样推给程序。
  - 没把事件存进库（2026-10-24 定）：两种做法只差 Rhodium 停下那一刻还没推出去的几条，不值得为它给“聊天正文不进库”再开一处例外。
- **按令牌隔离。** 每个程序只收到自己的 Bot 的事件，也只能经自己的 Bot 发消息。上游服务端都是广播给所有连接。
- **热插拔。** 登记程序、新建 Bot 都在运行中生效，不重启 `rhodium`。重启虽然不打断回合，但会断开所有程序的连接，“一句话生成 Bot”中途断一次不优雅。

后果：

- `login.adapter` 填 `rhodium`，不冒充 `qq`，免得客户端以为能用 Koishi 的 QQ 扩展。
- satori-python 改得快：2026-10-22 刚改过认账号的办法。程序的模板锁定版本，升级时用真 Entari 的测试兜住。
