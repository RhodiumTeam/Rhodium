# IM 层基于各平台官方 SDK 自写，不用 Bot 框架

这篇回答：Rhodium 怎样连接 QQ、Telegram 等 IM 平台，为什么不借用现成的 Bot 框架。

前置阅读：[术语表](../../GLOSSARY.md)、[产品说明](../product.md)、[调研摘要](../research.md)

状态：已接受（2026-10-21）

IM 层由 Rhodium 自己写，每个平台一个适配器。适配器底下用该平台的官方 SDK，没有官方的就用在维护的主流 SDK，例如 Telegram 的 grammY。适配器只报告平台能做什么，例如能否编辑、有没有按钮、长度上限。怎么降级，集中写在一处。

这样做，是因为北极星是 IM 体验，而细节全在平台差异里。QQ 的流式只能往后追加，被动回复有额度，重发的消息要能去重。框架把这些藏在它的适配器里，出了问题我们改不动。

## 考虑过的其他方案

- **以 Koishi、NoneBot 或 AstrBot 当宿主**。插件和 IM 连接在同一个进程里。AstrBot 就出过一个插件加载时卡住、整个进程起不来的问题（#8695）。空载内存 AstrBot 约 279MB，NoneBot 加四个适配器约 113MB（本机实测）。
- **把 satori.js 嵌进来当 IM 层**。它的主分支正在重构，Telegram 适配器 2025-11 之后没更新，QQ 适配器把被动回复窗口写死成 5 分钟（[调研摘要](../research.md) §5）。

## 后果

- 每加一个平台，就要写一个适配器。飞书、Discord、微信都在 v1 之后（[产品说明](../product.md) §13）。
- 平台的坑要自己填。例如 QQ 官方 Node SDK 默认用随机数当消息序号，重试时平台无法去重，Rhodium 要自己给出固定的序号。
