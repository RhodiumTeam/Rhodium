# Codex 每段对话一个托管进程，里面跑私有的 app-server

这篇回答：v1 之后接 Codex 时，Rhodium 怎么连它，为什么不连你本机共享的 Codex 后台服务。

前置阅读：[术语表](../../GLOSSARY.md)、[产品说明](../product.md)、[调研摘要](../research.md)

状态：已接受（2026-10-21）。它改掉了 [ADR-0002](0002-one-daemon-plus-holders.md) 和 [ADR-0009](0009-no-acp.md) 里 Codex 的接法。

Codex 和 pi 一样接：每段对话配一个托管进程，托管进程里跑一个只给这段对话用的 `codex app-server --listen stdio://`。Rhodium 不连你本机常驻的共享后台服务。

原来的打算是连共享后台服务。它的好处是客户端断开不打断回合，所以不用托管进程。2026-10-21 对照本机和 Codex 源码，发现三个问题：

- **认不出调用者。** 后台服务跑命令时，用的是它自己启动时的环境变量，不按客户端分。Rhodium 给每个槽位注入的 `RHODIUM_SLOT`、`RHODIUM_TOKEN` 到不了 Codex 跑的命令里。Codex 调 `rh` 时，Rhodium 认不出是哪个槽位，它的写操作全要你确认。
- **自动更新会打断回合。** 本机的后台服务旁边有一个自动更新的进程在跑。更新时后台服务重启，正在跑的回合被打断。要关掉它，得改 `~/.codex` 里的配置，而 Rhodium 不碰你的配置。
- **两边都能开回合。** 两个客户端可以同时订阅同一个线程，各自开回合。“同一段对话同一时刻只在一边运行”（[ADR-0001](0001-headless-first-exclusive-tui.md)）得由 Rhodium 自己挡。

私有的 app-server 放进托管进程以后，这三个问题都没了：

- 环境变量按进程注入，和 Claude、pi 一样，`rh` 认得出槽位。
- 你的后台服务更新、重启，碰不到 Rhodium 的进程。
- 这个进程只有 Rhodium 一个客户端。

Rhodium 重启不打断回合，这一点改由托管进程保证，和 Claude、pi 走同一套（[ADR-0002](0002-one-daemon-plus-holders.md)）。

## 考虑过的其他方案

- **连共享后台服务**（原计划）。好处是不用托管进程，所有线程共用一个进程，省内存。代价就是上面三条。
- **私有 app-server，但由 `rhodium` 直接拉起，不要托管进程**。私有的 app-server 读到输入结束就退出（空闲时实测），所以 `rhodium` 一重启，它就跟着没了，回合也断了。这正是 ADR-0002 要避开的坑。

## 后果

- 内存：每段运行中的 Codex 对话多一个进程，空闲时约 105MB（本机实测）。共享后台服务是所有线程共用一个，105–133MB。多出来的靠空闲回收兜底。
- 托管进程不解析协议，接 Codex 不用改它。
- `rh doctor` 不用再查共享后台服务的自动更新。
- 原来待验证的一条：切到 TUI 后，你终端里的 `codex` 和 Rhodium 的私有进程会不会写同一份对话记录。2026-10-27 实测：不会，见下面的补记。

## 补记：实测之后（2026-10-27）

决定不变。2026-10-27 用你的 Codex 登录在 codex-cli 0.162.1 上跑了探针，结论如下。

**不会两边同时写。**

- Codex 自己给每个线程加写锁：哪个进程开着线程，就由它拿着 `~/.codex/thread-writer-locks/<线程 ID>.lock` 的锁。
- 私有进程开着线程时，你在终端里 `codex resume` 它，Codex 提示它在别的程序里开着。私有进程退出后，终端接着写同一个记录文件。
- 反过来，终端开着时，私有进程接着这个线程会被拒（报 “already has an active writer”）。终端一退出，马上接得上。
- 所以风险不是写坏记录，而是被拒。被拒时 Rhodium 告诉你这段对话正在别处打开，消息留着。

**Rhodium 起的终端加 `--no-daemon`。**

- `codex resume` 默认连共享后台服务，后台服务没起就先替你起它。
- 加了 `--no-daemon`（0.156 起有），终端用自己进程里的服务：一退出就放开写锁，命令是终端的子进程，带着 pane 里注入的槽位身份，也不会替你拉起后台服务。
- 你自己开的 `codex` 不加它，照旧连后台服务。

**后台服务放开线程要等多久，看版本。**

- 原来写的“最多还挂 30 分钟”是 0.163 和 0.164 的默认值（1800 秒）。0.162.1 是 60 秒。
- 后台服务是 0.163 或 0.164 时，你自己的 codex 退出后，后台服务最长还占着线程 30 分钟。这期间 Rhodium 接不上这段对话。

**本机用不了 Codex 的沙箱。**

- 系统设置不让普通用户建隔离环境（`kernel.apparmor_restrict_unprivileged_userns = 1`），Codex 的沙箱起不来，每次启动都报告警。
- 所以 Rhodium 一律用 `danger-full-access`，不加沙箱。审批模式怎么对应见[产品说明](../product.md) §4.8。

**三个问题的判断都成立。**

- 环境变量按进程注入：`RHODIUM_SLOT`、`RHODIUM_TOKEN` 实测到得了 Codex 跑的命令里。
- 后台服务的自动更新只管它自己那个进程，碰不到私有进程。
- 私有进程只有 Rhodium 一个客户端。

另外两点：

- 私有进程崩了不会自己续跑被打断的回合，自动续跑只有共享后台服务有。Rhodium 照 pi 的办法写续跑提示。
- 回合中途关掉私有进程的输入，Codex 立刻杀掉回合。所以和 pi 一样，只在空闲时关。
