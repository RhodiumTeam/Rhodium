# 编码与审查规范

这篇回答：写代码和审查代码时，几件要判断的事按什么判断；审查者按它给意见定级。

前置阅读：[AGENTS.md](../../AGENTS.md)、[架构 §11 安全与访问](../architecture.md#11-安全与访问)

仓库的硬规矩（语言、文档、合规、测试隔离、额度）在 AGENTS.md 里，这里不重复。

## 防什么

- 威胁模型是单用户、单机：只有用户本人在用，所有进程都以用户的身份跑在他自己的一台机器上（架构 §11）。
- 碰不到的输入不加防御。例如 #59 的 `__proto__` 键、#68 的 JSON 嵌套深度。
- 毫秒级的竞态不加防御。

## 有意走的捷径

- 有意简化、知道上限的地方，加一条 `ponytail:` 开头的注释，写明上限和以后怎么升级。
- 例如 `// ponytail: one global lock; per-account locks if throughput matters.` 注释照 AGENTS.md 用英文。
- 这是 ponytail 的写法，它的 `/ponytail-debt` 能把这些注释收成一张清单。

## 意见怎么定级

- 会造成错误行为的，定为“必须修”。只给“建议修”不够。
- 极少碰到、修了又会加很多复杂性的，不修，在 PR 评论或相关 issue 里记一笔。这是用户 2026-10-22 定的原则。外部审查（例如 Codex）提的这类意见可以忽略。
- 只改一两处就能修的，照修。
- 只提影响行为或界面上看得见的意见。起名、代码格式这类纯风格的不提，除非违反了已经写下的规矩。
- 界面上看得见的毛病不算纯风格，要提。这是用户 2026-10-31 定的：
  - 改了网页界面的 PR，审查者要看截图：手机和宽屏，浅色和深色。
  - 实现的人开 PR 时在正文里写上截图在本机的路径。截图不提交进分支，也不传到外面的图床：里面可能有对话内容。没写就由审查者自己截。
  - 例如空着的一块、错位、框里套框、文字被截掉、浏览器原生的控件没处理（带箭头的滚动条之类）。
  - 改动碰到的组件上原来就有的这类毛病也要提，定为“建议修”，可以另开 issue，不能当没看见。

## 测试

- 测试先行（TDD）：先写测试，看它挂，再写实现让它过。撤掉实现，测试要挂。
- 测试不依赖录制素材里打过码的值。重录素材时这些值会变，测试就挂。
