# 飞书连接器规格

这篇回答：Rhodium 接飞书私聊要做成什么样、满足哪些需求、和飞书之间怎么说话、怎么测、怎么验收、明确不做什么，以及怎么拆工单。

前置阅读：[术语表](../../GLOSSARY.md)、[产品说明](../product.md)、[ADR-0008](../adr/0008-own-im-adapters.md)、[架构](../architecture.md)、[IM 文字与交互规范](../im-style.md)、[v1 规格](v1.md)、[IM 按钮行规格](im-buttons.md)

方向在第 33 轮拷问里定下，行为写进了[产品说明](../product.md) §5。写规格前，用一个测试应用在真飞书上跑了一遍探针（2026-10-26），你在手机上照着走完了 12 步。平台的限制和实测结果写在[架构](../architecture.md) §8 和 §5 第 7 步。这里不重复，只写需求、两边怎么说话、测试和交付。

这篇用到几个词：

- 应用：飞书开发者后台里的一个自建应用。开了机器人能力，它就是一个 [Bot](../../GLOSSARY.md)。凭据是 App ID 和 App Secret。
- 卡片：飞书的一种消息，能带按钮，发出去以后还能整张改。Rhodium 在飞书上发的字都是卡片。
- 长连接：飞书 SDK 和飞书之间的一条 WebSocket。消息和按钮都从它推过来，不用公网地址。
- [补拉](../../GLOSSARY.md)：见术语表。
- open_id：你在某个应用下的用户 ID，按应用分开。
- 测试应用：探针扫码建的“Rhodium 测试机”，在你当管理员的组织里。凭据在 `~/.config/rhodium-dev/feishu-dev.json`，以后开发和测试一直用它。

## 问题

**飞书上没法指挥 agent。**

- 你有自己当管理员的飞书组织，但 Rhodium 只接 QQ 和 Telegram。

**飞书和已有的两个平台不一样，照搬会出错。**

- 发出去还能改的只有卡片。卡片里的字在手机上只能整张全选。
- Rhodium 断线时你发的消息，飞书要过几分钟才重推，7 个多小时后就不推了。
- 一个组织里所有自建应用，共用一份每月的接口调用额度。
- 扫码建应用时带上附加配置，页面上建成了应用，`rh` 却拿不到凭据（只试过一次）。

## 方案

新加一个适配器 `src/feishu.ts`，基于飞书官方的 `@larksuiteoapi/node-sdk`。它和 Telegram 一样是能编辑的平台：一个回合一张卡片，不断改。差别都写在能力表和适配器里，路由和渲染器照能力表走。

手机上的飞书私聊大致是这样：

```
┌──────────────────────────────────────────┐
│ 我先看一下配置。                            │
│ ┃ [🔧 Read] src/config.ts                  │  ← 工具段，引用块
│ ┃ [🔧 Bash] npm test，正在运行              │
│ 配置里少了 X，我来补上，然后跑测试。          │
└──────────────────────────────────────────┘  ← 一张卡片，同一张最多每 3 秒改一次
┌──────────────────────────────────────────┐
│ 要运行这条命令，允许吗？                     │
│ rm -rf build && npm run build             │
│ 回别的话算拒绝，并转告它。                   │
│ [允许] [拒绝]                              │  ← 卡片上的按钮，按下以后卡片原地改
└──────────────────────────────────────────┘
 发送给 Rhodium                           /    ← 打 / 弹出 agent 的命令和 /rh_help
```

在 ssh 里建 Bot：

```
$ rh bot fs feishu
建飞书 Bot fs，建完绑定到 dispatcher/main。
页面上可以新建应用，也可以选已有的。选已有的，先停掉正连着它的程序：一个应用连着两处时，每条消息只随机推给其中一处。
用飞书扫下面的二维码，或在手机上点这个链接（1 小时内有效）：
https://…
（二维码）
扫码成功：App ID cli_a1b2c3d4e5f60789。
已把 Bot fs 写进配置文件并启用，绑定到 dispatcher/main。
扫码的飞书账号已记为你，Bot fs 不用再配对。
看板要显示你的飞书头像和名字，还要在开发者后台给这个应用加权限“获取用户基本信息”（contact:user.base:readonly），再发布一个版本。
```

这一步包含：

- 适配器：长连接收消息和按钮，收下才回执；卡片的发和改；图片和文件；`/` 菜单；Bot 和你的头像。
- 每次连上补拉这个私聊最近 24 小时，靠入站去重挡掉重推。
- 渲染器的飞书写法：转义 `&`、`<` 和 `:表情名:`，不是 http 的链接只留文字。
- `rh bot <名字> feishu`：扫码，或 `--paste` 粘贴 App ID 和密钥。
- 看板：飞书的平台标志。
- 一个假飞书，测试都接它。

## 用户故事

“用户”就是你本人。编号从 450 开始，前面的号已经有别的规格用了。

### 建 Bot

450. 作为用户，我想要在 ssh 里用 `rh bot <名字> feishu` 扫码建一个飞书 Bot，扫码的账号就记为我，不用再配对，建完马上能用，以便在飞书里像在 QQ、Telegram 里一样指挥 agent。
451. 作为用户，我想要扫码页上也能选一个已有的应用，`rh bot` 提醒我先停掉正连着它的程序，以便把以前建的 Bot 接进来。
452. 作为用户，我想要扫码不方便时，能粘贴 App ID 和密钥（密钥不回显），照提示在后台配好，再用 `rh pair` 配对，以便用在开发者后台手建的应用。
453. 作为用户，我想要用 Lark（飞书国际版）账号扫码时，`rh bot` 直接告诉我暂不支持，以便不白建一个用不了的 Bot。
454. 作为用户，我想要看板和拓扑图上有飞书 Bot 的头像，以及我在飞书的头像和名字；缺权限时 `rh bot` 告诉我去后台加哪一项，以便和别的平台一样认得出是哪个窗口。

### 收发

455. 作为用户，我想要在飞书私聊里发文字和富文本，agent 收到的是我写的字，以便直接派活。
456. 作为用户，我想要一个回合的过程和最终回复在同一张卡片里，同一张最多每 3 秒改一次，工具段、代码块、表格照 agent 写的显示，以便在手机上看着进展，又不多耗调用次数。
457. 作为用户，我想要卡片里的字照写的显示：agent 写的 `:OK:`、`<font>` 不变成表情和颜色，Rhodium 拼进来的名字和路径里的 `_`、`*` 也不变成格式，以便读到的就是写的。
458. 作为用户，我想要卡片在会话列表和通知里显示最新的一句，以便不点进去也知道到哪了。
459. 作为用户，我想要飞书不认卡片里的 Markdown 时，这条照样发出去，改成纯文字，以便消息不会因为格式丢掉。
460. 作为用户，我想要提问、面板、`/status` 这些带按钮的消息在飞书里也有按钮，按下以后卡片原地改，答完的按钮撤掉，按了失效的按钮弹一句提示，以便和在 Telegram 里一样点着用。
461. 作为用户，我想要在飞书输入框里打 `/` 看到当前 agent 的命令和 `/rh_help`，换 agent 后跟着变，以便不用记命令。

### 别的消息

462. 作为用户，我想要发图片、文件、表情包给 agent，agent 拿得到；agent 用 `rh send me --file` 发的图片和文件也能在飞书里收到，以便传截图和日志。
463. 作为用户，我想要回复某条旧消息时，agent 看得到我引用的原文，以便接着那句说。
464. 作为用户，我想要把一段聊天记录合并转发给 Bot 时，agent 收到里面的文字，谁说的用“我、A、B”标出，图片和文件写明没取，以便把别处的讨论交给 agent。
465. 作为用户，我想要发语音时 Rhodium 回一句暂不支持、不交给 agent，以便知道要改用文字。

### 不丢不重

466. 作为用户，我想要 Rhodium 停着、重启或断网时我在飞书发的消息，连上后马上交给 agent，不用等飞书几分钟后的重推；晚到 5 分钟以上的，agent 看得到我是什么时候发的，以便升级时也不怕丢话。
467. 作为用户，我想要同一条消息不会交给 agent 两次，哪怕飞书过几分钟又推一遍，以便“部署到生产”不会做两遍。
468. 作为用户，我想要连接半死不活时 Rhodium 自己发现、重连；一直连不上时，和别的 Bot 一样标成故障，经别的 Bot 告诉我，以便知道飞书那边断了。
469. 作为用户，我想要飞书本月的接口额度用完时，该发给我的话改从别的 Bot 发，开头说明原本要发到飞书私聊，以便不漏掉 agent 的回复。

## 实现决定

### 已定的大方向

- 只做国内飞书，不做 Lark。只做私聊。
- 扫码为主，扫码的人就是你，不用配对。也能粘贴凭据，再配对。
- 一张卡片从头改到尾，同一张最多每 3 秒改一次。用整张改（PATCH），不用飞书的流式卡片（CardKit）：
  - 回合常常超过 10 分钟，流式卡片 10 分钟后自己关掉。
  - 按卡片实体发出的卡片，不能再整张改。
  - 每 3 秒改一次已经够看，流式还多两次调用。
- 不做按钮行。`/` 菜单经斜杠命令接口推。
- 每次连上都补拉这个私聊最近 24 小时，按消息 ID 去重。
- 语音先回暂不支持。合并转发展开成文字。
- SDK 只用 `Client` 和 `WSClient`，不用它的 `channel` 模块：那里的错误码表把限流当成了“被撤回”和“没权限”。
- SDK 写死 1.76.0，有飞书 Bot 时才加载。`rhodium` 大约多 4MB；加载后进程多约 36MB 内存（2026-10-26 实测）。

### 这些没单独问，直接定了

不同意就说，改起来都只动一处：

| 定了什么 | 为什么 |
|---|---|
| 表情包当图片交给 agent | 文档说下不了，实测能下，是 JPEG。小表情本来就是 `[OK]` 这样的字 |
| 补拉回来的旧消息照常交给 agent，来源行带发送时间 | 和 QQ 续上断点、Telegram 接着拉一样；超过 5 分钟的本来就带发送时间 |
| 补拉不早于这个 Bot 第一次接进这个应用的时刻 | 选了已有应用时，私聊里以前那边处理过的话不该交给 agent |
| 私聊窗口的 ID 用你的 open_id，不用私聊的 chat_id | 路由、头像、`/` 菜单都假定私聊窗口的 ID 就是你的用户 ID |
| 改卡片的间隔做成配置项 `durations.feishuEdit`，默认 3 秒 | 先看每月调用次数再调；改配置重启就行 |
| 卡片的摘要取正文最后一个非空行的前 50 字 | 会话列表里看到最新进展，不是“[卡片]” |
| 不是 http、https 的链接只留文字 | Claude 常写指向本地文件的链接，飞书收到就拒收整张卡片 |
| 多于 3 张表格、不是飞书的图片地址，不清理 | 少见；拒收了整张退回纯文字，字不丢。多于 3 张表格会不会拒收还没查清，见[要先实测的](#要先实测的)第 10 条 |
| Rhodium 自己的纯文字用卡片里的纯文本元素发，不转义 | 照原样显示最稳；它照样能改、能带按钮 |
| 合并转发里，这个 Bot 自己的话标“Bot” | 标成 A 会让 agent 以为是别人 |
| 合并转发最多展开 50 条，嵌套的缩进两格 | 和飞书官方的封装一样 |
| 视频按文件交 | agent 看不了视频，给路径就够 |
| 按下的提示最多等 2.5 秒，等不到就不弹 | 飞书要 3 秒内拿到应答 |
| `/` 菜单只管 Rhodium 会推的命令名 | 选已有应用时，它可能有自己的斜杠命令 |
| 文件下载不分块 | 不带 Range 下载 10.6MB 成功了，和 cc-connect 说的 2MB 上限不符 |
| `--api-root` 也给飞书用，只用于测试 | 和 Telegram 一样，不多一个选项 |
| 不做本机按 App ID 加锁 | 同一份配置里本来不收重复的 App ID；正式和开发用不同的应用 |

### 手机上复制卡片里的字（定为 A）

探针结果：手机上点卡片里的字，总是整张全选，选不了一部分。电脑版能选一部分。

2026-10-27 定了 A：照旧一张卡片。要复制就整张复制，再删掉不要的。手机上复制一小段不方便，换来每个回合不多一条消息、不多一次调用。

- 没选的 B：回合结束后，在卡片下面再发一条富文本消息，只放最终回复。C：同 B，只在最终回复里有代码块时才补发。
- 单独发出来方便复制的那一条（[IM 文字与交互规范 §11.5](../im-style.md#115-复制按钮)）只有要复制的那段话，手机上整张全选正好就是它。

### 配置

```toml
[bots.fs]
platform = "feishu"
appId = "cli_a1b2c3d4e5f60789"
secret = "…"
owner = "ou_…"   # 扫码时 rh bot 写上；粘贴的没有，靠 rh pair
target = "dispatcher/main"
```

- `apiRoot`：只给测试用。开放平台和扫码的地址都换成它。
- `durations.feishuEdit`：同一张卡片两次改之间至少隔多久，默认 `3s`。
- 库里的 meta 表多两行。键都带 App ID，同一个名字下换了应用不会串，和 `telegramOffset:`、`qqSession:` 一样：
  - `feishuChat:<App ID>`：你和 Bot 私聊的 chat_id，以 `oc_` 开头，补拉要用。
    - 从 Rhodium 自己发出消息的应答里记，应答带 `chat_id`。Rhodium 只给你发，所以记下的一定是你的私聊。
    - 和记着的不一样就换掉，例如重新配对到了别的账号。
    - 不从收到的消息记：粘贴建的 Bot，适配器不知道谁是你，别人先发来的会被记下，你的私聊就一直补拉不到。
  - `feishuSince:<Bot 行 ID>:<App ID>`：这一行 Bot 第一次接进这个应用的时刻。`takeIn` 时没有这一行就记下现在。
    - 为什么带 Bot 行：入站去重按“聊天窗口 + 消息 ID”，窗口挂在 Bot 行下，Bot 行又按配置里的名字找（`src/daemon.ts` 的 `takeIn`）。
    - 改了 `[bots.<名字>]` 的名字再重启，或 `rh bot rm` 去掉、以后再加回同一个应用，都是一行新的 Bot，没有入站记录。只按 App ID 记，补拉会把 24 小时里处理过的话再交一遍。

### 窗口 ID

- 私聊窗口的平台 ID 用你的 open_id。发消息用 `receive_id_type=open_id`。
- 为什么：路由、头像、`/` 菜单都假定私聊窗口的 ID 就是你在这个 Bot 下的用户 ID，QQ、Telegram 都是这样。飞书私聊自己的 chat_id 是另一个值，只在补拉时用。
- open_id 按应用分开，所以每个飞书 Bot 都要单独认你，和 QQ 一样。

### 长连接和回执

- `WSClient` 带 `wsConfig.pingTimeout` 10 秒、`handshakeTimeoutMs` 10 秒。不设，半死的连接发现不了：SDK 默认不看心跳。
- 重连交给 SDK：第一次随机等 0 到 30 秒，之后每 2 分钟一次，间隔由飞书定。
- 连接状态照[架构 §8.6](../architecture.md#86-故障隔离)报给 `connected`：
  - 连上（`onReady`、`onReconnected`）报一次 `true`。
  - 断开（`onReconnecting`）报一次 `false`。SDK 不报每次重试，适配器看 `getConnectionStatus()` 的 `reconnectAttempts`，每涨一次再报一次 `false`。
  - SDK 放弃了（`onError`，例如凭据失效）：报 `false`，关掉它，照 Telegram 的退避等一会儿，再起一个新的。
- 迭代停下时 `close({ force: true })`。不加 `force`，旧连接会自己接着重连（node-sdk 的 issue #197）。
- SDK 的日志只留警告和错误，经适配器的 `log` 打出。日志里不出现密钥。
- 收到事件，处理函数等 `rhodium` 把它收下才返回，也就是等生成器被下一次拉取。和 Telegram 的“下一次拉取才算读过”一样。
  - 返回了，SDK 回执成功。收下之前出错，处理函数抛错，SDK 回执失败，飞书按 15 秒、5 分钟、1 小时、6 小时重推。
  - 收下用了 3 秒以上（例如先下载一个大文件），飞书当推送失败，过 15 秒重推。入站去重挡掉，不用管。
- 模板里还订阅了几个用不上的事件：表情回应、Bot 进出群、文档评论。各注册一个什么都不做的处理函数，收到就回执，免得飞书一直重推。
- 只收私聊（`chat_type` 是 `p2p`）。群里来的消息照样回执，不交给 `rhodium`。

### 补拉

- 每次连上（`onReady`、`onReconnected`）补拉一次：
  - `GET /open-apis/im/v1/messages`，`container_id_type=chat`，`container_id` 是 `feishuChat`，`sort_type=ByCreateTimeAsc`，一页 50 条，翻完。
  - 从 `feishuSince` 和“现在减 24 小时”里晚的那个，拉到现在。
  - 只留 `sender_type` 是 `user` 的。列表里也有 Bot 自己发的卡片。
  - 每条照推来的消息一样转成入站消息，排进同一个生成器。
- 补拉交完之前推来的事件先等着，补拉的交完再按推来的先后交。不然断线时发的旧消息会排在新消息后面。等过 3 秒的，飞书当推送失败，15 秒后重推，入站去重挡掉。
- 转换之前先查入站表，补拉到的和推来的都查：
  - `takeIn` 给适配器一个 `seen(chat, messageId)`，查的就是入站去重那张表、同一个键。
  - 已经收下的跳过：推来的照样回执，不下载附件，不展开合并转发，不交给 `rhodium`。
  - 不查的话，每次连上都把 24 小时里的图片、文件、表情包重下一遍，每次下载都算额度；`rhodium` 先下载附件再去重（`src/daemon.ts` 的 `listen`），真正漏掉的又排在最后。
  - `rhodium` 的入站去重照旧兜底。
- 已经收下的、之后飞书又重推的，都由入站去重挡掉（[架构 §7.3](../architecture.md#73-入站去重)）。补拉到的消息收下时也就记进了入站表。探针正是漏了这一步，飞书 6 分半后的重推被当成了新消息。
- 还不知道 `feishuChat` 时不补拉。这时断线期间的消息靠飞书的重推，晚 6 分半左右。
- 补拉到的消息照常交给 agent。它的时间是你发的时间，晚到超过 `durations.sentAtAfter`（默认 5 分钟）的，来源行带上发送时间（[架构 §6.1](../architecture.md#61-统一接口)）。
- 补拉失败（例如限流）记一行日志，不重试。飞书的重推还会来。
- 为什么是 24 小时：和 Telegram 在服务器上留消息的时长一样；飞书自己的重推约 7 小时 20 分后就停了。

### 收到的消息

| 飞书的消息 | 交给 `rhodium` 的 |
|---|---|
| `text` | 文字。表情面板里的小表情本来就是 `[OK]` 这样的字。整段被 `<p>…</p>` 包着的（转发时附的留言就是这样）转成字：一段一行，`<br>` 换行，标签去掉，`&lt;` 这类写法转回字符。所以你打的 `<p>x</p>` 也收成 `x`。别的照原样交，例如打的 `<b>`。合并转发里的 `text` 也这样转 |
| `post`（富文本） | 用 `content`，不用 `content_v2`，拼成文字：标题一行；每段一行；链接写成“文字（地址）”，文字和地址一样时只写地址；`@` 写成“@名字”；代码块用围栏包起来；分割线写 `---`；粗体这些样式去掉。里面的图片作为附件 |
| `image` | 图片附件，按 `type=image` 下载 |
| `file` | 文件附件，按 `type=file` 下载。名字用消息里的 `file_name`：下载时响应头里的中文名是乱码 |
| `media`（视频） | 文件附件 |
| `sticker`（表情包） | 图片附件，按 `type=image` 下载 |
| `audio`（语音） | 只报是语音（`voice`）。路由回一句暂不支持，和 Telegram 一样 |
| `merge_forward`（合并转发） | 展开成文字，见下 |
| 回复了某条消息（带 `parent_id`） | 引用，`ref` 是 `parent_id`。原文由路由从库里找，和 QQ 一样（[架构 §8.3](../architecture.md#83-媒体)） |
| 按下卡片上的按钮（`card.action.trigger`） | 按下，见[按钮](#按钮) |
| 别的（位置、名片、日程……） | 不交，和 Telegram 一样 |

- 消息 ID 用 `message_id`。入站去重按它，不按 `event_id`：重推的 `event_id` 是新的。
- 时间用消息的 `create_time`（毫秒）。
- 发送人用 `sender_id.open_id`。
- 下载下来的图片按内容认格式，例如你发的图是 WebP（[架构 §8.3](../architecture.md#83-媒体)本来就这样做）。

合并转发：

- `GET /open-apis/im/v1/messages/<合并转发的消息 ID>` 一次拿回所有子消息。每条带 `upper_message_id`，按它拼成树。
- 写成这样：

  ```
  [合并转发，5 条]
  我 17:15：这条消息是断线时发送的
  Bot 17:16：[卡片]
  我 17:16：[图片，没取]
  A 17:18：好的
    第二行缩进两格
  A 17:20：[合并转发，1 条]
    B 10-25 09:01：方案在群公告里
  ```

  - 你是“我”，这个 Bot 自己是“Bot”，别人按出现的先后是 A、B、C……
  - 时间和来源行一样：当天写 `17:15`，别的日子写 `10-25 17:15`。
  - 图片、文件、视频、表情包不取，写 `[图片，没取]`、`[文件 名字，没取]`、`[视频，没取]`、`[表情包，没取]`。语音写 `[语音]`。别的种类写飞书的类型名，例如 `[location]`。
  - 卡片写 `[卡片]`：飞书读回的卡片只是一句“请升级至最新版本客户端”。
  - 嵌套的转发缩进两格。最多 50 条，多出的写“还有 N 条没展开”。
- 拉不到（例如限流）写 `[合并转发，没取到]`，和空的 `[合并转发，0 条]` 分开。
- 只有合并转发本身是一条入站消息。子消息的 ID 和原来那条一样（探针实测），记进入站表会让以后真推来的那条被当成重复。

### 发出的卡片

- 发的都是 JSON 2.0 卡片（`msg_type` 为 `interactive`），铺满宽度（`width_mode: "fill"`），`update_multi: true`。图片和文件除外，见下。
- 正文：
  - 有 `markdown` 时，放进一个 `markdown` 元素。
  - 只有 `text` 时（Rhodium 自己的纯文字），放进一个纯文本元素（`div` 加 `plain_text`），照原样显示，不用转义。
  - 飞书拒收 Markdown 的那张（报 230099；说是表格超过 3 张会拒收，还没查清，见[要先实测的](#要先实测的)第 10 条），同一条改用纯文本元素再发一次、或再改一次。和 Telegram 拒收 rich message 时一样。
- 按钮跟在正文后面，见[按钮](#按钮)。
- 摘要（`config.summary`，会话列表和通知里显示的那句）：`text` 最后一个非空行的前 50 字。每次改都跟着换。
- 一条最多 4000 字（`maxTextLength`）。卡片和改卡片的请求最多 30KB，4000 字转义后也放得下。
- 只有第一次发会提醒你，之后的改不提醒，和 Telegram 一样。
- 适配器在内存里记着最近发过或改过的 500 张卡片的内容，用在两处：
  - 按下按钮时，带上那张卡片的文字（`button.text`），面板的“取消”要用它。
  - 撤按钮（`dropButtons`）：把记着的内容去掉按钮再整张改一次。不知道内容（例如 `rhodium` 重启过），报失败。按钮留着，按了路由照旧答“这个按钮已经失效了”。
  - 为什么记：飞书读回的卡片只是一句占位，不能拿回来改。
- 你回复 Rhodium 发的卡片时，原文也是从出站记录里找（[架构 §8.3](../architecture.md#83-媒体)），不读回卡片。

图片和文件：

- 图片先上传（`POST /open-apis/im/v1/images`，`image_type=message`），拿到的 key 再发一条 `image` 消息。
  - 飞书拒收的图片改按文件再传一次，发成 `file` 消息。例如分辨率超限（234039：GIF 超过 2000x2000，别的超过 12000x12000），飞书文档就是让这样传。上传本身不发消息，所以不会收到两份。额度用完、限流、没回音的不重传。
- 文件先上传（`POST /open-apis/im/v1/files`）。`file_type` 按扩展名填 `pdf`、`doc`、`xls`、`ppt`（`.docx`、`.xlsx`、`.pptx` 也算），别的都是 `stream`。再发一条 `file` 消息。
  - `opus`、`mp4` 也填 `stream`：这两种是给语音消息、视频消息用的，Rhodium 一律发文件消息。node-sdk 自带的发送封装也是这样配的。
- 上限：图片 10MB，文件 30MB（`maxFileBytes`）。空文件飞书不收。
- 图片和文件消息不带字，也不改。路由本来就先发文字，再每个文件各发一条（[架构 §8.3](../architecture.md#83-媒体)）。

结果怎么报（`SendResult`）：

| 飞书回的 | 报成 | 说明 |
|---|---|---|
| `code` 为 0 | 已发 | |
| 99991403 | 失败，带 `quota`，不重试。发和改都是 | 本月额度用完，见下。飞书回它时 HTTP 状态也是 429，所以先认它，再认 429。不然当限流重试 3 次、报成 `flood`，路由不会改经别的 Bot 发 |
| 230020、99991400、别的 HTTP 429 | 等响应头 `x-ogw-ratelimit-reset` 给的秒数再试，最多 3 次、最多等 60 秒；还不行，失败，带 `flood` | 限流时飞书没收这条，和 Telegram 的 429 一样 |
| 别的错误码 | 失败 | 飞书明确说了不 |
| 超时、断网、5xx | 结局不明 | 飞书可能已经收了（[架构 §7.4](../architecture.md#74-出站结局不明的消息不自动重发)） |

额度用完（99991403）：

- 发送失败带 `quota`，路由照 QQ 主动消息额度用完那样，改经别的 Bot 发，开头写“飞书私聊那边发不出去，改发在这里。”（[架构 §8.2](../architecture.md#82-发送策略)）。
- 路由的 `refused` 现在按 QQ 的被动回复处理带了入站消息的那种。不是 QQ 的 Bot，不管带没带，一律改经别的 Bot 发。不改的话，飞书会同一条一直重发。
- 改卡片失败带 `quota`，照编辑失败改发一条新消息。新消息也发不出，同样改经别的 Bot。这个回合之后就在那边接着改，不会每 3 秒多一条。
- 下一条照旧先试飞书。被拒的调用不算额度，下个月 1 号额度回来，自然就恢复了。
- 不额外通知：改发的消息开头已经说了。

### 改卡片的节奏

- 能力表加 `editEvery`：同一条消息两次改之间至少隔多久，从它发出或上一次改算起。飞书是 `durations.feishuEdit`，Telegram 不设。
- 只管回合的过程消息，也就是 `src/daemon.ts` 的编辑队列。按下面板后原地往下走、撤按钮，照旧马上改：那是你在等的。
- 同一私聊的请求照旧按 `sendLimit` 排。飞书每秒 5 个：发给同一个人每秒最多 5 条。
- 编辑队列本来就只留最新内容，等的这 3 秒里来的字都并进下一次。
- 一个两分钟的回合约 1 次发、40 次改。探针连改 10 次，每次 0.7 到 0.9 秒，没碰到限流。

### 按钮

- 一行按钮放在一个分栏里（`column_set`，`flex_mode: "flow"`），每个按钮一栏，宽度 `auto`。行照 [IM 文字与交互规范 §11.2](../im-style.md#112-排布) 排。
- 按钮的数据放进回调的 `value`：`{"d": "<数据>"}`。
- 选项和主动作用 `primary` 样式。`muted` 的（取消、返回、翻页）用 `default`。
- 飞书没有复制按钮，能力表不设 `copy`。路由照旧把那段话单独发一条。
- 飞书没有“填进输入框”的按钮。带 `fill` 的照普通按钮按下。
- 回调走长连接，来的是普通的事件帧，SDK 直接能收（探针实测）。
- 交给 `rhodium` 的按下：
  - `sender` 和 `chat` 都用 `operator.open_id`，也就是按的人。不用私聊的对方，也不用 `context.open_chat_id`。
    - 为什么：路由只拿 `sender` 和你比，看是不是你按的（`src/router.ts` 的 `im`）。填成私聊的对方，卡片被转给别人时，别人按下就能替你答审批、跑面板命令。
    - 别人按的，`sender` 是他，路由当不是本人，什么也不做。
  - 消息 ID 用事件 ID。飞书只重推事件，不重推回调。
  - `button.data` 是 `value.d`，`button.message` 是 `context.open_message_id`，`button.text` 是记着的那张卡片的文字。
  - 时间取收到的时刻。回调的 `create_time` 是微秒，和消息的不一样。
- 应答要放在回调的返回值里，3 秒内：
  - 处理函数等 `answerPress` 给出提示，最多 2.5 秒。
  - 有提示，返回 `{"toast": {"type": "info", "content": "<提示>"}}`。没有、或等不到，返回 `{}`。
  - 过了 2.5 秒才来的提示就不弹了。
- 按下以后的结果照 Telegram：整张改被按的那张卡片，面板原地往下走，撤掉按钮。

### `/` 菜单

- 用斜杠命令接口 `/open-apis/application/v7/app_slash_commands` 的列出、新建、修改、删除。SDK 没有封装，直接发请求。
- 能力表：`menu.scope` 为 `global`，一个应用一份；`maxItems` 100；没有 `row`。
- `setMenu` 先列出应用现有的命令，再：
  - 少的新建。命令名不带 `/`，说明放在 `description.default_value`。
  - 说明变了的改。
  - 多的删掉，只删 Rhodium 的：哪个 agent 的 `/` 菜单里会有的命令名（`slashMenu` 的全集）。别的不动。
- 新建按 `/` 菜单的顺序一条一条来。
- 推上去要过几分钟客户端才看到。文档说缓存约 5 分钟；探针推完 12 分钟后你看到了，更早有没有不知道。
- 你选一条，发来的就是普通文字，例如 `/rh_help`，和手打的一样，路由不用另做什么。
- 换 agent：Claude 换到 pi，删 `/ultracode` 一条；换回来，再建一条。
- 2026-10-26 实测：换 pi 后菜单确实会变，但客户端什么时候刷新说不准。把这个 Bot 的会话标成“完成”，再点回来，能看到新的。

### 头像和名字

- Bot 的头像：`GET /open-apis/bot/v3/info` 给的 `avatar_url`，不用登录就能下载。
- 你的头像和名字：`GET /open-apis/contact/v3/users/<open_id>?user_id_type=open_id` 的 `name` 和 `avatar.avatar_240`。
  - 要权限 `contact:user.base:readonly`。默认权限清单里没有。没有时只回 open_id，`profile` 就不给这两样（[架构 §7.9](../architecture.md#79-头像缓存)本来就这样处理）。
  - 通讯录接口不算每月额度。
- 看板和拓扑图加飞书的平台标志（`web/src/faces.tsx` 的 `Mark`）。
- 工具行默认用详细写法，按能力表算（能编辑的平台），不按平台名。`src/board.ts` 的 `verboseIn` 现在写死了 Telegram，要跟着改。

### `rh bot`

`rh bot <名字> feishu [<工作区/槽位>] [--paste] [--api-root <地址>]`

- 和 QQ、Telegram 一样问两次 `rhodium`：先查名字和槽位，再带着凭据写进配置（[架构 §8.5](../architecture.md#85-建-bot-与配对)）。
- 凭据：`appId`、`secret` 必有，扫码的多一个 `owner`。配置里已经有同一个 App ID 的 Bot，不收，说“要再建一个，扫码时选新建应用”。
- `--paste` 只给飞书。`--api-root` 给 Telegram 和飞书，只用于测试。
- `rh bot` 的说明（`src/commands.ts`）加上飞书。

扫码（不带 `--paste`）：

- 用 SDK 的 `registerApp`，先定为不带 `appPreset` 和 `addons`。
  - 探针第一次带了名字、`preset: false`、权限、事件和回调，页面上建成了应用（你确认过），`rh` 这边却一直拿不到凭据。
  - 第二次不带，选的是第一次建的应用，拿到了。
  - 两条结论都只试过一次。新建应用不带附加配置、只带权限，各再试一次，见[要先实测的](#要先实测的)第 6、7 条。
- 先提醒选已有应用的事，再在终端里画二维码，同时给链接。手机上 ssh 扫不了自己屏幕上的码，点链接就行，你建测试应用时就是点的链接。
- 链接 1 小时内有效：飞书回的是 3600 秒，不是文档说的 10 分钟。过期了换一个，说一句“链接过期了，正在换一个……”。Ctrl+C 退出。
- 应用名在扫码页上起，`rh` 不预填。
- 拿到 App ID、密钥和扫码人的 open_id 以后：
  - 扫码的是 Lark 账号（`tenant_brand` 为 `lark`）：不收，说“暂不支持 Lark（飞书国际版）。刚建的应用在 Lark 的开发者后台，用不着可以删掉。”
  - 用这组凭据问一次 Bot 信息。扫码人的 open_id 和 Bot 自己的一样，就不记主人，改走 `rh pair`。cc-connect 防过这种情况。
  - 问不到 Bot 信息，也不记主人，改走 `rh pair`，说一句原因。凭据是飞书刚给的，不当成飞书不认。
  - 否则 `owner` 就是扫码人。

粘贴（`--paste`）：

- 先问 App ID（回显），再问 App Secret（不回显）。
- 用它们换一次访问凭证（`POST /open-apis/auth/v3/tenant_access_token/internal`），说“App ID 和密钥有效。”飞书不认，说“飞书不认这组 App ID 和密钥：<原因>”，原因里没有密钥。
  - 不问 Bot 信息：要先开机器人能力、发布版本才问得到。刚在后台建的应用还没有，这两步在下面列的几步里。
- 写进配置、连上以后，提示后台要做的几步，再给配对码：

  ```
  在开发者后台给这个应用做完这几步，再私聊 Bot 发配对码：
  1. 添加机器人能力。
  2. 事件与回调：订阅方式选长连接；加事件“接收消息”（im.message.receive_v1）；加回调“卡片回传交互”（card.action.trigger）。
  3. 发布一个版本。
  ```

  - 先连上再去后台：后台选长连接时，飞书要看到有程序连着才让保存。
  - 没加卡片回调，按按钮时飞书报 200340，回调到不了 Rhodium。

都要：

- 建完问一次权限清单（`GET /open-apis/application/v6/scopes`）。没有 `contact:user.base:readonly`，多说一句怎么加，见[方案](#方案)里的样子。

### 渲染器的飞书写法

- 能力表的 `markdown.extensions` 是 `["html", "emoji"]`。`emoji` 是新加的，指 `:名字:` 这种表情写法。先转义 `html`，再转义 `emoji`。
- agent 的话，代码以外：
  - `&` 写成 `&amp;`，`<` 写成 `&lt;`。不然 `<font color='red'>` 真的变成红字，`<at>` 会去 @ 人。
  - `:OK:` 这样的，前一个冒号写成 `&#58;`。不然变成橙色的 OK 表情。
  - 别的照 GFM 原样放。`__init__.py` 变粗体、`~~删除线~~` 有删除线，和 Telegram 上一样，那是 agent 自己的 Markdown。
- 不是 http、https 的链接 `[文字](地址)`，只留文字。不然飞书拒收整张卡片（230001），只能退回纯文字。
- 查询命令的回复（`md` 模板）里拼进来的值：先照 Telegram 加反斜杠，再照上面转义（[架构 §8.2](../architecture.md#82-发送策略)）。
- 系统提示里给 agent 的格式说明（`src/prompt.ts`）：飞书私聊一条最多 4000 字；可以用 Markdown；HTML 标签、`:表情名:` 会按原文显示。

### 要先实测的

都用测试应用，在手机上看。

1. 第 1 张工单开头：卡片里 `&lt;`、`&amp;` 显示成 `<`、`&`；`&#58;OK:` 显示成 `:OK:`，不是表情。
   - 不行，就在两个冒号之间插一个零宽空格（U+200B），像 QQ 上打断 `](` 那样。
   - 2026-10-26 已经看到：`&#42;`、`&amp;` 有效；`\*`、`\#`、`1\.` 有效，反斜杠不显示；不认识的 `<T>`、`<details>` 原样；`:OK:` 变表情；`<font>` 变红字；不带分号的 `&reg` 原样。
   - 还要看：`\_`、`` \` ``、`\~`、`\[`、`\]`。查询回复里拼进来的值靠它们。
2. 第 1 张工单开头：卡片里的纯文本元素（`div` 加 `plain_text`）照原样显示，换行都在。不行，就改用 `markdown` 元素，照查询回复的办法转义成原样显示。
3. 第 3 张工单：按钮回调返回 `{}` 时客户端不报错。有说法会报 99992354。报错的话，没有提示时回一句“已收到”。
4. 第 3 张工单：一行两个、一行四个按钮在手机上截不截字，和 IM 文字与交互规范 §11.2 的字宽对不对得上。
5. 第 3 张工单：`/` 菜单在客户端里是不是按建的先后排。不是，就看按什么排，照着建。
6. 第 5 张工单开头：在测试组织里扫码新建一个应用，不带附加配置，看 `rh` 拿不拿得到凭据。探针第二次扫码选的是已有应用，新建这条路还没走过。试完在后台删掉这个应用。
7. 第 5 张工单开头：只带 `addons` 的权限（用得上的，加 `contact:user.base:readonly`），别的都不带，看拿不拿得到凭据。
   - 拿得到：照第 33 轮的决定，扫码带这份权限。
   - 拿不到：照旧不带。`rh bot` 列出默认清单里用不上的权限，说可以在后台删掉，和加 `contact:user.base:readonly` 放在同一个版本里发布。
8. 第 5 张工单：扫码带上 `appId` 和要加的权限（更新已有应用的那条路），能不能把 `contact:user.base:readonly` 加上。能，`rh bot` 缺这项时给这个链接；不能，照旧提示去后台加。
9. 转发时附的留言里带 `<`、`&`、两行、粗体，飞书怎么写。2026-10-26 只见过一行字的：`text` 消息，回复那条转发，文字是 `<p>这里是什么？</p>`。别的写法是照 HTML 猜的。
10. 一张卡片里多于 3 张表格是不是真会拒收。2026-10-26 在正式实例上，一张带 5 张 Markdown 表格的卡片发出去了，电脑版飞书上显示正常，没退回纯文字。

## 你来验收

每张工单合并前，开发用的 agent 从源码另起一个 `rhodium`，跑成 `rhodium-test-` 开头的单元，配置只有测试应用这一个 Bot，你在飞书里私聊“Rhodium 测试机”。不碰正式实例。

2026-10-26 在正式实例上验过，都通过：

- 收发；`/rh_use` 翻页；`/rh_help`。
- 图片、文件、表情包。
- 合并转发。里面的图片和文件不取，照设计。
- 语音回暂不支持。
- 审批和提问的按钮。
- 停 70 秒再起来，停着时发的那句补交给了 agent；8 分钟内没有交第二次。
- 换 pi 后 `/` 菜单会变，什么时候刷新见 [`/` 菜单](#-菜单)。
- `--paste`：在一次性的测试实例上用测试应用粘贴建 Bot，在飞书里发配对码，配对成功。

还没验：

- 拒收后退回纯文字。带 5 张表格的卡片发出去了，没被拒收，见[要先实测的](#要先实测的)第 10 条。

收发：

- 发一句，让 Claude 读几个文件再回答：一张卡片，工具段在引用块里，大约 3 秒一跳，最后一段是回答。会话列表里显示最新的一句。
- 让 agent 原样回 `:OK:`、`<font color='red'>红</font>`、`a < b && c`：都显示成字，不是表情、红字。
- 发 `/rh_ls`、`/status`：标题和粗体正常，名字里带 `_` 的槽位原样显示。
- 等[要先实测的](#要先实测的)第 10 条查清飞书拒收什么，再让 agent 回一段会被拒收的话：整张退回纯文字，字都在。
- 发一段富文本，带粗体、链接、代码块：agent 收到的是字，链接和代码都在。

按钮和菜单：

- 开审批模式，让 agent 跑一条命令：卡片上有[允许][拒绝]。按允许，卡片写上答复，按钮撤掉。再让它问一条，在看板上答掉：飞书里那张卡片也写上答复，按钮撤掉。
- `/rh_use` 翻页、选一个、再开一次按“取消”：卡片原地变。
- 打 `/`：看到 11 条命令。`/rh_agent` 换成 pi，几分钟后变成 10 条。选 `/rh_help`，弹出首页。

别的消息：

- 发一张图、一个文件、一个表情包：agent 都拿得到，文件名对。
- 回复 Rhodium 的一张卡片说“这里再展开”：agent 看得到那张卡片的原文。
- 转发一段和别人的聊天记录：agent 收到“我、A”标好的文字，图片写明没取。
- 发一段语音：Rhodium 回暂不支持，agent 没收到。
- 让 agent 用 `rh send me --file` 发一张图和一个 PDF：都收到了。

不丢不重：

- 在 ssh 里停掉这个 `rhodium` 单元，在飞书发一句，一分钟后再起来：几秒内 agent 收到，来源行带发送时间。等 7 分钟，agent 没再收到一次。

建 Bot：

- 停掉验收用的 `rhodium`，另起一个，用测试应用的 App ID 和密钥 `rh bot <名字> feishu --paste`：照提示在飞书里私聊 Bot 发配对码，配对成功。
- 第 5 张工单合并、你同意装到正式实例以后：在正式实例上 `rh bot <名字> feishu`，点链接，选新建应用。建完不用配对，私聊发一句就有回应。
- 照提示给正式的应用加“获取用户基本信息”、发版本：第二天（或重启 `rhodium` 后）拓扑图上有你的飞书头像和名字。
